Root owns the standalone scene, native metadata, prefab references and the existing MatchClient. This lane adds only the menu, exact content resolver, party state coordinator and tests. It does not edit the shared lobby or deploy public maps.

Initialize a `WordboundPartyMenu` with the committed `OnlineServices/production-client.json` text, exact `items.json` and `rules.json` text, a stable release map-pool ID, and optional independently approved public-content JSON. Default registry is empty and Quick Play stays disabled. The menu validates the production origin, Photon app, issuer, key ID and public-key fingerprint before opening its HTTP client.

Set `BeginMatchRequested` to one `Func<WordboundPartyLaunchContext, CancellationToken, Task>`. Root creates a fresh MatchClient and calls its `StartMatch` with context Coordinator, Verifier, Verified, Content.Mode, Course, Geometry, Items and Rules, the native body/carrier prefabs, `menu.PhotonAppId`, the registered gameplay SceneRef, context FreshJoin and Content.PhysicalPuzzles. The context's selected seed and six content hashes must remain unchanged. Items/rules getters return copies. Race proof construction includes the exact rule-book source and effective rules fingerprint.

Set `ReturnRequested` to the active MatchClient's asynchronous `ReturnToParty`. Its Task completing is not server confirmation because MatchClient catches request errors. Only wire its successful ReturnedToParty event to `menu.NotifyReturned(context.Verified.Match.MatchId)`; the ID overload ignores late events from an old match. The menu deliberately preserves its context when the Return task completes without that confirmation event. Wire Failed to menu.ShowFailure only while that MatchClient remains the active one. Successful start hides the menu. `Visible` gates drawing only; the component must remain enabled so coalesced polling can refresh guest access during gameplay. Do not destroy the menu while its MatchClient is active. `WorkshopRequested` and `CloseRequested` are available only without an active match, reservation or pending mutation; root may hide/show the same menu when switching panels.

The launch context starts with an unknown initialization outcome. Root calls `MarkClientInitialized()` once it has initialized the MatchClient session. If startup validation failed before any client/session initialization and root has cleaned up the attempted composition, call `ConfirmNoClientInitialized()` instead. These states cannot be reversed or interchanged. Only the latter enables the menu's direct coordinator-return fallback; it still clears context only after a successful server response. An unknown/initialized client must use the normal stop-and-confirmed-event path.

FreshJoin rotates the guest refresh credential, retrieves and verifies a fresh signed start certificate and admission for the pinned match/roster/content, then obtains a fresh app-bound Photon ticket. All credentials remain in memory. No PlayerPrefs or log stores tokens. Optional ResumeGuest accepts a protected refresh token plus the retained map seed; it recovers party membership via `/v1/me`. Without the seed the party remains visible for safe leave, but content readiness fails closed.

Party invitations encode party UUID, private invite and deterministic seed. Private-room invitations additionally carry mode, format, region, protocol and map-pool version; Fill remains the joining party's explicit choice. All members must click Ready before the leader queues. Custom Fill is a separate queue and each joining member must explicitly verify/accept the matching installed content before admission readiness. Arbitrary downloaded workshop content is not silently trusted.

Unknown mutation outcomes retain the exact original HTTP body, party revision and idempotency key. The menu blocks replacement actions until retry resolves that outcome. Polling is coalesced, serialized with mutations and cancelled on disposal; a pending user mutation prevents a preceding poll from automatically accepting a match. A returned match cannot auto-launch again.

Public registration is an explicit data handoff: `WordboundPublicCourseRegistry.RegistrationJson(testedCourses)` produces the exact BuiltIn content array used by the service's `BUILTIN_CONTENT_JSON`. Producing the array does not approve/deploy it. Root must validate actual gameplay, deploy the matching registry and ship exactly that trusted array before enabling Quick Play.
