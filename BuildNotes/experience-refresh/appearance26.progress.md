## Recommended minimum contract

**Decision:** support the already-approved Classic/Candy/Arcade choices as host-admitted, match-frozen cosmetic preferences. All 24 enabled entries among the current 50 catalogue items list Candy and Arcade (read-only JSON inspection). Keep raw items/rules and every existing content binding unchanged. No new item catalogue or PackingClub admission is needed for this slice. Preserve the local shop's equip/unlock behavior, but do not describe that local check as anti-cheat purchase verification. If server-enforced ownership is a requirement, a service-backed entitlement system is additional scope; sending Career or an `owned` flag is not a substitute.

### Authority stages and fields

1. **Capture once at launch.** `WordboundLauncher.BeginMatch` -> `WordboundMatchClient.StartMatch` -> session carries a cloned, canonical selection from the lobby/local profile. Do not pass mutable GameConfig objects or read PlayerPrefs from the host rule engine. Add one shared pure cosmetic validator using the bound ItemCatalogue plus the immutable, installed wardrobe policy. Local profile repair can select the default outfit before sending; malformed network requests must be rejected rather than silently rescued by `Wardrobe.Sanitize`.
2. **Admit through readiness.** For the next explicit wire contract, Ready carries the roster hash and bounded serialized appearance. Derive the actor exclusively from the existing authenticated PlayerRef/gate/lease checks in `ReadyAdmittedPeer`; the message must not choose player ID, seat, team, health or inventory. Treat the local host through that same validation path. Store at most one accepted value per original actor/current connection; identical Ready retransmits are idempotent, conflicting values after acceptance are rejected. A replacement connection before bootstrap must invalidate/rebind its pending value under the existing connection tuple fences. No in-match outfit update command is required in this first slice.
3. **Seal before first checkpoint.** After the complete original roster is ready and after `BootstrapConnections` has been captured/revalidated, but before `PublishCheckpointCore(..., true, ...)`, initialize the complete appearance map through a host-only authority operation. The operation requires tick zero, no already-published initial snapshot, the exact original actor set, and a valid writer/connection fence at the session boundary. Mutate only each actor's existing `MatchActorState.Appearance`; copy all health, stamina, cooldown, input sequence, equipment, attack and defense fields unchanged. The existing snapshot hash/ACK barrier then includes every outfit. Clear pending admission data with RunScope invalidation; never reseal a restored match from new preferences.
4. **Restore exactly.** The existing actor appearance field and item `ThrowerSkin` field survive snapshot encoding/checkpoint/migration. Validate canonical cosmetic values on snapshot import with the same installed policy. Reconnect receives the committed value for its original actor; changed local preferences take effect in the next match. Do not trust a client's proposed appearance as proof that a committed snapshot is correct, and do not replace the snapshot's captured throw finish with the current lobby choice.
5. **Capture crafted throws on the host.** In `AuthoritativeMatch` Throw, read the actual item in the authenticated actor's authoritative slot/carried inventory before Economy removes it. Resolve its canonical item ID against the bound catalogue and the actor's admitted per-recipe selection, applying the existing `Appearance.Pick` fallback. Pass that resolved finish to `Economy.Throw`; Economy already stores it only for Crafted origin and clears it on Settle. Client command value, target text and model path must not choose the skin. Damage, reach, collider, mass, throw speed, durability, timing and entity budgets remain catalogue/rule-derived.
6. **Present from the corresponding state.** Actor dressing and held-item recreation already consume snapshot appearance. Index authoritative economy items for world-body presentation even when no melee animation is active (the current temporary inventoryItems cache is populated only when melee is needed). Resolve the active body's finish from matching `item:<id>` + item state/origin/revision: crafted Thrown uses captured ThrowerSkin; world/dropped/settled and noncrafted throws keep Classic. Include the resolved finish in visual cache invalidation and create its prefab/metadata as one pair. A new holder uses that holder's per-recipe skin. Reconcile network-body and checkpoint timing so a stale item snapshot cannot repaint a newer thrown body; retain the last matching presentation or Classic until a matching state is available. Missing local art may fall back visually without modifying authoritative state.

No new authoritative actor field is needed. The changed data are existing `MatchActorState.Appearance` and crafted thrown-item `ThrowerSkin`; a small bounded session-side pending map is new transient state. No new NetworkBody field is required if the presentation consumes an adequately matched snapshot, though its latency must be verified. Geometry registry IDs do not enter actor statistics.

### Canonical validation and boundedness

- Keep the existing actor appearance bound of 2,048 characters and additionally bound UTF-8 bytes to 2,048 for the new control payload. Keep the existing 24,576-byte control frame ceiling, eight-seat roster ceiling, and 64-character skin ceiling. Do not enlarge general command payloads (currently 1,024 bytes and restricted 96-character value grammar) to carry outfits.
- Require the exact canonical `Outfit.Serialize` form: duplicate/unknown slots or recipes, extra separators, malformed entries, delimiter-containing IDs and noncanonical ordering are rejected. A strict parser or bounded parse plus exact serialize round-trip must precede semantic validation; current Deserialize alone loses duplicates and ignored suffixes.
- Clothing IDs, slot compatibility, required/excluded pieces and colours must pass the pinned wardrobe policy. Each item-skin key must be an ordinal canonical enabled item ID and the finish must satisfy that bound item's HasSkin. Use the enabled catalogue as the finite per-recipe domain; the mode's existing crafting permissions stay unchanged. Omitted skin means Classic. Do not accept arbitrary paths, renderer names, materials, stats or an unapproved PackingClub string.
- Pin the wardrobe policy to the application contract, since wardrobe JSON is not part of the current ItemSourceHash/CatalogueHash. A release must freeze its expected bytes/policy; changing it later needs an explicit cosmetic-policy compatibility decision. Do not conceal a new policy by mutating ItemCatalogue after hashing. Use the same policy for initial admission and restored snapshot validation.
- Require canonical allowed captured skin for new crafted Thrown state. Do not impose a blanket `ThrowerSkin == null` rule on all other states without first checking Economy transitions such as picking up an in-flight item; the existing lifecycle can retain unused metadata until a later throw/settle. Visual resolution remains conditional on origin/state. No silent rewrite of an already-hashed snapshot is acceptable.

## Versioning and release consequence

Populating the existing appearance/throwerSkin fields does not by itself require changing `MatchSnapshot.Schema = 3` or `CanonicalVersion = 3`: their representation already includes these values, and changing only cosmetics correctly changes the complete state hash. Test gameplay equivalence by excluding those explicitly cosmetic fields, not by demanding identical full snapshot hashes.

The **new Ready shape is a wire change**. Old decoders reject additional fields, and unknown wire kinds also fail. The safest initial rollout is a distinct application protocol that pins the cosmetic policy and fences incompatible peers, with existing snapshot schema/canonical encoding retained if no structural snapshot field changes. This is not a client-only switch: `FusionSession.cs:149` uses settings.ProtocolVersion for Fusion AppVersion; `OnlineContracts.cs:16` includes it in pool keys; `OnlineServices/src/checkpoints.ts:96,192` currently pins wordbound-v3; `bundles.ts:10` also pins v3; checkpoint schema/canonicalVersion are separately pinned at checkpoints.ts:116-117. Public export wrappers also name the protocol. Root must plan the coordinated protocol/Worker/workshop/export-wrapper release and in-flight v3 policy before enabling the new Ready payload. That plan is outside this report-only lane.

This can retain **exact raw items/rules and approved mode/format/content rows**: `OnlineServices/shared/public-bindings.mjs` rows contain content/mode/format rather than protocol, and the new appearance is not a CatalogueHash input. It does not promise the complete client public-catalogue export wrapper remains byte-identical if its protocol field changes. Avoid claiming “no release work” merely because no item catalogue is added.

If root requires retaining v3 with no service release, a fully tested capability/legacy fallback design is needed first. No suitable negotiation exists in the current Ready/Admission fields. Do not silently change v3, exploit ignored message fields, or assume all peers/migration hosts are upgraded. An old host can preserve a restored appearance string yet still capture empty skin on future throws, so decoding an existing snapshot alone does not establish feature compatibility.
