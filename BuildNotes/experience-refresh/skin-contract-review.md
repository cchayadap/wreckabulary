## Decision

The optional geometry registry is a safe render-only foundation. Add exactly `(Items/BAT, PackingClub)` and `(Items/SHIELD, PackingClub)`, keep every existing fallback, and leave `items.json` byte-identical in this slice. Do not advertise it as a fully synchronized selectable online skin yet: current selection rejects this new ID, and online appearance/throw initialization is not wired. Both findings have high source confidence; no rendered result or multiplayer behavior was exercised here.

The smallest immediately reviewable delivery is the registry, shared prefab/metadata resolution, Inspector authoring and an explicit authoring preview. Enabling PackingClub in the player wardrobe needs a deliberate follow-on choice: a separate cosmetic allowlist, or a new canonical catalogue release. Registering the prefab alone, aliasing PackingClub to Candy/Classic, or mutating a parsed match catalogue after hashing would obscure that boundary.

## Bounded implementation recommendation

1. Use an Inspector-editable asset with unique, ordinal `(canonical modelKey, skinId)` pairs; require a render prefab, icon, finite nondegenerate bounds, finite grip and positive bounded held scale. Validate serialized Inspector edits as well as programmatic setters; invalidate lookup caches after edits. Reject duplicate pairs and prefab physics/network/gameplay scripts before instantiation. `Online/Presentation/WordboundVisualProfile.cs:49` already defines a useful render-only validation policy; avoid an Art-to-Online assembly dependency when sharing it. PackingClub IDs should exclude Outfit delimiters `|;=:` and fit the existing 64-character throw-skin bound.
2. Have `Art/ModelVisual.cs:7` and `Online/Presentation/WordboundVisualResolver.cs:60` resolve the same entry. Preserve explicit `WordboundVisualProfile.TryInstantiate` precedence. For an exact optional skin use its prefab and its own bounds/grip/heldScale together; otherwise retain the existing Wordbound Classic collection and original ModelLibrary/material fallback. Missing optional collection/entry must not make normal items disappear. Do not let the old Wordbound collection's metadata describe a new skin prefab.
3. Keep canonical body size, colliders, attack reach/damage, block behavior, durability, speed, recipes and server state unchanged. Resolver fitting already normalizes visual bounds to supplied canonical dimensions (`WordboundVisualResolver.cs:100,125`); skin bounds are source-art metadata, not new game geometry. Limit held scale/grip freedom to approved visual fitting, and review BAT reach silhouette and SHIELD coverage/occlusion at gameplay distance. Unchanged stats alone do not prove equal visual readability.
4. Preserve authored PackingClub materials. `Art/MaterialLibrary.cs:44` can replace recognized material families with Classic when the requested finish is absent; do not unconditionally recolor the new prefab. Retain TactileMaterials cleanup behavior when applicable.
5. `UI/Lobby/LobbyStage.cs:113` currently checks `item.HasSkin`, prechecks `Items/` plus the word and spawns that constructed key. Use `item.Model` for preview resolution and an explicit approved skin source; do not bypass admission merely because a prefab exists. `UI/GeneratedItemArt.cs:26` only accepts item ID and a Wordbound flag: add an optional skin-aware path if the collection icon is expected in UI, retaining the old API/fallback.

For a hash-preserving selectable skin, explicitly split cosmetic admission from the immutable rules catalogue: validate the canonical item/model plus an installed cosmetic allowlist, retain Classic fallback on clients without art, and use that same decision in shop/equip, preview and Wordbound presentation. Avoid globally making `Appearance.Pick` accept arbitrary strings. This is a small separate contract review, not a catalogue mutation hidden in an asset importer. Specify the free ownership/grant rule and the authoritative appearance source before claiming remote visibility. Existing serialized string fields can carry PackingClub, but that is not evidence that transport initialization, admission or migration behavior is implemented.
