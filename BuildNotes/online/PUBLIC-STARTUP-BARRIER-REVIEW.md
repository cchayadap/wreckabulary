# Public startup readiness and snapshot barrier review

STATUS: COMPLETE, read-only source/evidence diagnosis. No implementation or native run by this lane. Integration inspected at `6c1937ab44d305ff5a3ba0edab53b1f1ecd0735b`; retained execution receipt is source `3aa74c6f`. Neither failure below is assumed to be a service/network fault.

Scope: current integration FusionSession, GameplayController, session gate and snapshot/physics paths. Determine scene readiness, bootstrap durability, Begin, per-peer snapshot ACK and first canonical host tick ordering, including migration/rejoin constraints. Preserve authentication, epochs, terms, timeouts and atomic snapshot validation.

## Finding

There is a complete-roster **scene/admission** barrier and a client-side validated-snapshot barrier. There is **no host barrier awaiting any peer's initial canonical snapshot ACK**. After durable bootstrap publication and election-marker seeding, the host may compose and advance while clients are still receiving the bootstrap. This is an actual ordering property, not proof that adding a barrier cures all observed failures.

An initial-only wait for each original admitted peer's exact bootstrap ACK before sending Begin is a justified bounded candidate. Existing ACK can arrive before Begin and does not require native gameplay body replication, so that ordering is not circular. Waiting for client GameplayReady or all replicated bodies at the same point would be circular under the current composition contract. No source change is proposed for approval as part of this report.

## Minimal candidate contract and boundaries

1. Limit an initial barrier to `requiresCompleteRoster == true` for the current RunScope. Pin the exact bootstrap mark from that durable publication and exact original ready roster/current authenticated connections. Record only matching ACKs for that run/term/epoch/mark/peer. Recheck current writer, roster, leases, cancellation and runner identity before release; a stale ACK or disconnect cannot silently reduce the required set.
2. Keep host GameplayReady/transport admission to commands false until all required bootstrap ACKs. SDK ticks, reliable receive callbacks, Poll, writer renewal and connection renewal must continue. Existing client ReceiveSnapshot can validate/import/ACK with Begin still false. Send Begin once only after the existing election prerequisite and barrier succeed, then retain current atomic BeginHost composition and first-tick fences.
3. Do not confuse `sentMarks` becoming empty after disconnect with successful ACK. Do not infer receipt from a peer merely sending Ready, from a current coordinator head, from the Photon election marker, or from client requests to skip synchronization. Existing authenticated SnapshotAck proves receipt by that peer, not authority over state.
4. A bounded host wait must remain inside an explicitly retained existing startup limit. Currently the90 s original-roster limit in Poll is conditional on `!gate.Started`; gate.Started becomes true before bootstrap. Merely inserting an unbounded wait would be unsafe, especially if the final chunk never arrives (the receiver's10 s check executes only on another chunk). An implementation must explicitly select/enforce the existing initial90 s absolute boundary without resetting it or extending any transfer/lease/recovery deadline. This requires source/test review before approval; no timeout has been changed here.
5. Do not apply an all-original-roster wait to rejoin/migration. RestoreForMigration preserves original seats and120 s reconnect deadlines but permits resuming with an admitted ready survivor. Late Ready during existing gameplay reconnects its seat and sends Begin/current committed state while the host keeps running. A later rejoin barrier would be a separate behavior decision, not this initial-only fix. Pending initial ACK state must be discarded on InvalidateRun/Stop/recovery, not survive a new Runner or writer term.
6. Waiting for remote physical bodies before Begin is not this candidate: those bodies are currently created only by BeginHost after session.GameplayReady. A full body-ready barrier would require a separate compose-while-frozen state plus additional signal and reentrancy proof. It should not be smuggled into this change. Likewise, one synchronous BeginHost composition can still stall lease/network processing after ACK; this proposal removes pre-import steady ticks, not all startup or steady performance work.

## Minimum proof before adopting a barrier

- Hold/delay one required bootstrap ACK without changing receiver deadlines: both scenes/admissions and durable head/election may be ready, but host canonical advances must remain0 until the exact last ACK; then exactly one start and real input/command/ACK follow.
- Wrong mark/epoch/peer, duplicate ACK, disconnect/reconnect during pending start, explicit Stop, writer expiry and invalidated RunScope cannot release the old start. Retain existing signature/identity/connection checks. Missing ACK must terminate inside the original absolute startup boundary while renewal continues.
- Preserve first-start2/4/8 full-roster semantics, late rejoin without globally stopping existing play, and actual elected-host survivor recovery without waiting for returned/disconnected original seats.
- Rerun the same public Team/Brawl native entry cases and compare first canonical host tick against observed bootstrap ACK, keeping all timings unchanged. Distinguish initial-transfer improvement from later-transfer/input failures. Existing tests' Ready predicate does not assert this ordering and therefore cannot alone guard the new contract.

A minimal observation accompanying any later candidate can reuse the existing exact ReplicaReceived/ReplicaAcknowledged events and HostAdvanced test callback to assert ordering without payload logging. Capture only first-bootstrap marker equality, ACK peer counts and first-advance order in tests; no new production telemetry is necessary for that regression. Additional chunk timing remains a separate optional diagnostic if later transfer failures persist.

Input independently corroborated the read-only noncircular ordering and narrow initial-only recommendation. It confirmed that accepted ACKs must be recorded explicitly, regular controller publication is blocked before hostReady, and survivor recovery cannot reuse a complete-original-roster barrier. This is design corroboration only; no implementation, execution or causal performance benefit has been reviewed.
