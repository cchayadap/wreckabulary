## Installed SDK trace — a concrete time-provider gate

Read-only Mono.Cecil inspection of the same pinned Fusion.Runtime DLL establishes the following order and guards. No game assembly was executed, SDK changed, debugger attached or heavy job launched.

1. `NetworkRunnerUpdaterDefault.InvokeUpdate`, IL0044–0080, selects the simulation's update-time mode and passes Unity `Time.unscaledDeltaTime` for mode0 (`UnscaledDeltaTime`), or `Time.deltaTime` for mode1. `SimulationConfig` constructor sets mode0 at IL0012–0014; WordboundFusionConfiguration.CreateLocal constructs that default, changes peer/prefab/network/tick settings but does not replace the update-time mode, and Create only changes heap settings. The checked global config also says mode0. This is source/default proof, not a new live configuration readback.
2. `Simulation.Update`, IL002d–0063, runs BeforeUpdate and NetworkRecv **before** updating its time provider. Runtime configuration and the provider's IsRunning flag gate that update. Client RecvPacket first calls StateReplicator.RecvPacket, sets `_stateReceived`, then appends the packet tick to its history and feeds timing feedback. LatestServerTick reads the history's newest tick. Therefore confirmed-server knowledge can change before local clock advancement or simulation.
3. **`ClientTimeProvider.Update`, IL0042–0088, returns without advancing its input/local/interpolation clocks when the supplied delta is greater than1.0 second.** It resets the frame-delta check and exits before feedback correction in that method. Its fixed trace text says time will not advance because the frame delta is too big. `ServerTimeProvider.Update`, IL0001–000a, simply adds the supplied delta. A skipped time update does not itself prove zero simulation ticks: already accumulated target time or clock changes while processing received feedback may still permit work.
4. CalculateForwardTicks and CalculateInputTicks require runtime configuration and a running time provider. Each computes a target from its respective LocalTime/InputTime multiplied by TickRate, caps that target at LatestServerTick+TickRate, subtracts the respective current tick, divides by stride and clamps the count to0..TickRate. A newer server frontier alone therefore does not force positive work. At60Hz the maximum per calculation is60 ticks.
5. `Simulation.Update` calls Client.BeforeSimulation only when its calculated forward count is positive (IL00b0–00d3). When `_stateReceived` is true, that method removes buffered inputs whose ticks are at or below LatestServerTick (IL0084–00ca); for client/server topology it also resets the state tick to LatestServerTick before any resimulation (IL00e5–0135). If no forward simulation is eligible, this normal cleanup/reset path is not reached that update. Client NoSimulation can still send queued packets after its one-second stopwatch threshold; it does not advance these clocks or prune the input buffer.
6. Client.PollInput invokes the application OnInput callback before trying Buffer.Add (IL01db–01f9). When Add rejects a full buffer, PollInput releases that new input and returns null; the application read count has already increased. Simulation.Update increments InputTick before polling and ignores PollInput's returned value. Thus InputTick and local movement reads are not buffer acceptance or host receipt counters. The client buffer capacity is the resolved client tick rate (60 here by configuration), and Add emits the observed generic warning when count equals capacity. Client BeforeSimulation removes old inputs; resetting the client simulation clears the buffer. This bounded buffer design must not be changed merely because warnings occurred.
